# 用户与 Telegram 配对

默认自主注册普通用户。管理员由 `.env` 中的初始账户配置创建；普通用户共享只读生产视图，只能管理自己的通知。补录、复位、报警确认以及 FUXA 网页入口要求管理员。管理员不能通过个人 API 查看别人的 Telegram 投递。

core 保存用户、密码散列和 12 小时 Cookie 会话。notifier 保存 Telegram 绑定、配对码、偏好、个人投递和 Bot 更新游标；它不读取 core 数据库。

流程：私聊同一个 Bot 发 `/start` → Bot 返回 8 位配对码 → 已登录用户在网页个人通知页提交 → notifier 原子消费并建立一对一绑定 → 网页配置炉子、通知类别、恢复通知和总开关。配对码 10 分钟过期，再次 /start 刷新旧码；已绑定者不会收到可被另一账户接管的新码。

实现顺序：先更新 OpenAPI，再加账户与 Cookie、配对服务、按偏好分发、最后接前端。默认通知类别为扫码异常、MES 异常、设备连接异常、入炉流程异常；不增加静默时段或频率规则。

账户身份来自服务端会话，不接受调用方指定 userId 或审计操作人。服务内部 userId 路径只能由 Bearer 认证的 core 调用。配对请求与登录做小范围限流；密码不存明文，会话密钥与配对码不进入日志。

每个新事件按当时的绑定和偏好生成独立投递；发送前再次检查绑定与偏好。解绑或暂停后取消尚未发送的投递。旧版没有用户归属的积压消息保留记录，但不发给新配对用户。

FUXA 保持集群内服务，原本机 31081 入口改由 core 的管理员认证代理提供。摄像头预览和公共业务 API 也需要登录；设备内部协议与已运行的入炉状态机保持原职责。

验证限于账户/权限边界、配对过期与单次消费、个人通知隔离及实际 Bot 配对过程，不重跑入炉故障矩阵。

演示环境曾在 OrbStack 完成真实 Bot 配对，用户收到了配对码并完成网页绑定。公开仓库不包含 Bot Token、管理员密码、配对码或个人 Chat ID；新部署需使用自己的 Bot。
